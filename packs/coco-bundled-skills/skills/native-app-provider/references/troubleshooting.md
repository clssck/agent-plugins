# Native App Troubleshooting

## Common Issues

| Issue | Cause | Fix |
|-------|-------|-----|
| "Package already exists" | Package name conflict | Use `CREATE APPLICATION PACKAGE IF NOT EXISTS` or choose a different name |
| Account-level object creation fails (compute pool, warehouse, database, EAI, security integration) despite correct privileges and app spec | An object with the same name already exists in the account — account-level names are globally unique | Run `SHOW <object_type>` (e.g., `SHOW COMPUTE POOLS`, `SHOW WAREHOUSES`, `SHOW EXTERNAL ACCESS INTEGRATIONS`) to check for name collisions — do NOT drop the existing object, do NOT speculate about missing privileges until name collisions are ruled out |
| "Insufficient privileges" | Depends on the operation that failed | Identify which operation triggered the error and load the corresponding sub-skill from the routing table in `../SKILL.md` — each sub-skill has its own privilege checks |
| "Stage not found" | Stage doesn't exist or wrong path | Verify stage with `SHOW STAGES IN SCHEMA <app_pkg>.stage_content` |
| "Cannot find manifest" | `manifest.yml` not at stage root | Ensure PUT uploads `manifest.yml` to the root of the stage path |
| "Invalid manifest" | YAML syntax error or missing required field | Validate YAML syntax; ensure `manifest_version` and `artifacts.setup_script` are present |
| PUT command fails | Wrong file path or permissions | Use absolute paths with `file://` prefix; check local file permissions |
| "Setup script failed" | SQL error in setup script | Enable debug mode, check error message, fix script |
| "Object already exists" | Non-idempotent CREATE statement | Use `CREATE ... IF NOT EXISTS` for stateful and account-level objects (tables, schemas, compute pools, services) and `CREATE OR REPLACE` for stateless objects (procedures, functions) |
| Object not visible to consumer | Missing application role grant | Add `GRANT ... TO APPLICATION ROLE` in setup script |
| Schema "does not exist or not authorized" | Missing schema-level grant | Every non-versioned schema the consumer accesses needs `GRANT USAGE ON SCHEMA <schema> TO APPLICATION ROLE <role>` — without it, Snowflake hides the entire schema even if objects inside it were individually granted |
| SPCS container sees empty `access_token` file (0 bytes) after install | Service was created at install while `SECURITY_INTEGRATION` / `EXTERNAL_ACCESS` specs were still PENDING (manifest_version: 1). The OAuth fetch failed silently, and SPCS does **not** auto-rotate the mount when specs are later approved. | **Fix:** With `manifest_version: 2`, app specs are auto-granted — no deferral needed, the service can be created directly in the setup script. With `manifest_version: 1`, adopt the Deferred Service Creation Pattern: use a consumer-invoked `start_service()` procedure called after approving both specs. See `ref-spcs-setup-script.md` § Deferred Service Creation — manifest_version: 1 (manual trigger). **Legacy workaround only:** on an existing broken install you cannot redeploy, `suspend_service` + `resume_service` forces SPCS to re-mount the secret — but ship the fix in the next version rather than shipping this as the supported install flow. |
| SPCS service can't reach external endpoint even after specs approved | EAI is missing from `CREATE SERVICE`, or was placed in the spec YAML instead of SQL | Attach EAI in SQL: `CREATE SERVICE ... EXTERNAL_ACCESS_INTEGRATIONS = (<eai>)`. Do **not** put `EXTERNAL_ACCESS_INTEGRATIONS` in the YAML. On upgrades, re-apply with `ALTER SERVICE ... SET EXTERNAL_ACCESS_INTEGRATIONS = (<eai>)`. See `ref-spcs-setup-script.md` § Attaching EAI to a Service. |
| SPCS service upgrade didn't pick up new EAI / new secret | `CREATE SERVICE IF NOT EXISTS` is a no-op when the service exists; `version_initializer` used only `ALTER SERVICE FROM SPECIFICATION_FILE` (YAML changes) but didn't re-apply the EAI | Route `version_init` through `core.create_or_update_service()` — its ALTER branch always re-applies both the spec file AND `SET EXTERNAL_ACCESS_INTEGRATIONS`, then calls `SYSTEM$WAIT_FOR_SERVICES`. See `ref-spcs-setup-script.md` § Deferred Service Creation Pattern. |
| `CREATE SERVICE` fails with "Reference definition '...' is missing a reference association" (Approach B) | Service was created before all referenced EAI/SECRET references were bound. `CREATE SERVICE` fails outright on unbound references. | Defer service creation to the register callback. The reconciler (`core.create_or_update_service`) gates on `SYSTEM$GET_REFERENCE(...)` returning non-null for every required reference before issuing `CREATE SERVICE`. See `ref-spcs-setup-script.md` § Deferred Service Creation Pattern → Reconciler — Approach B. |
| `version_init` fails on fresh install with "Service '...' does not exist" after adopting deferred creation | `version_init` still runs `ALTER SERVICE ... FROM SPECIFICATION_FILE` directly. On first install the service does not exist yet. | Replace the direct `ALTER SERVICE` in `version_init` with `CALL core.create_or_update_service();`. The reconciler handles the "service absent + gate unmet" case as a no-op success and only issues ALTER/CREATE when it is safe. See `ref-spcs-setup-script.md` § Deferred Service Creation Pattern → Wiring the callbacks. |
| `specification_action` callback fires but service is not created (optional edge case — `specification_action` is not required for manifest_version: 2 Approach A since app specs are auto-granted) | `is_service_ready_to_deploy()` still reports false — typically only one of the two specs (SI or EAI) is APPROVED, or the `SHOW APPROVED SPECIFICATIONS` query matches on the wrong column. Three common pitfalls: (1) using `SHOW APPROVED SPECIFICATIONS IN APPLICATION` inside the app — this looks for a literal app named "APPLICATION"; use `SHOW APPROVED SPECIFICATIONS` without `IN APPLICATION` when running inside the app context. (2) Checking the `"type"` column for `'SECURITY INTEGRATION'` / `'EXTERNAL ACCESS'` (with spaces) — the actual values are `'SECURITY_INTEGRATION'` / `'EXTERNAL_ACCESS'` (underscored). (3) Missing `GRANT USAGE ON PROCEDURE callbacks.on_spec_approved_or_declined(...) TO APPLICATION ROLE` — without this grant, the callback is never invoked. | Verify: (a) `is_service_ready_to_deploy()` uses `SHOW APPROVED SPECIFICATIONS` (no `IN APPLICATION`), (b) the `WHERE` clause checks `'SECURITY_INTEGRATION'` and `'EXTERNAL_ACCESS'` (underscored), (c) the `callbacks.on_spec_approved_or_declined` procedure is granted to an application role. The callback fires once per spec — the reconciler no-ops until both are APPROVED. |
| Service token breaks mid-upgrade after spec sequence number bumped | Provider changed the SI/EAI spec definition, so the sequence number bumped and both specs went back to `PENDING`. Direct `ALTER SERVICE` in `version_init` pushed the new YAML while the EAI was unapproved — token fetch fails. | Route `version_init` through `core.create_or_update_service()`. When the gate is temporarily unmet (specs re-PENDING) the reconciler returns "gate temporarily unmet; leaving service on current spec" — the service keeps running on the old spec. Consumer re-approves → `on_spec_approved_or_declined` fires → reconciler ALTERs cleanly. See `ref-spcs-setup-script.md` § Deferred Service Creation Pattern → Failure semantics. |
| `SYSTEM$WAIT_FOR_SERVICES` fails with "service is suspending or suspended" | `SYSTEM$WAIT_FOR_SERVICES` was called while the service is in SUSPENDED state — it has no running instances to wait on. | Add `ALTER SERVICE ... RESUME` (wrapped in `BEGIN ... EXCEPTION WHEN OTHER THEN NULL; END`) before the `SYSTEM$WAIT_FOR_SERVICES` call. The exception guard makes the RESUME a no-op when the service is already running. |
| `"Error parsing manifest.yml: Manifest field 'privileges' may only specify a single attribute per item"` — privileges declared but not applied (KB 000008743) | The `description:` line under each privilege is not indented with a tab. The YAML parser requires exactly one tab indent before `description:` below each privilege name. | Add a `<tab>` indent before `description:` below each privilege declaration. Correct format: `privileges:\n  - EXECUTE TASK:\n      description: "Needed to run tasks"` |
| `st.image()` fails in a Streamlit component inside a native app (KB 000009393) | `st.image()` with file paths is blocked in the native app framework. | Base64-encode the image and use `st.image(image_string)`. Create an `image_loader.py` helper: `import base64; mime = filepath.split('.')[-1].lower(); data = open(filepath,'rb').read(); st.image(f'data:image/{mime};base64,{base64.b64encode(data).decode()}')` |
| Images in `readme.md` do not display; HTML elements ignored (KB 000009565) | The native app framework supports only basic Markdown syntax in `readme.md`; HTML is not supported; image files referenced by path are not supported. | Base64-encode images and embed them as inline data URIs: `![alt](data:image/png;base64,<encoded>)`. HTML tags are not supported and will be ignored. |
| Stored procedures inside a shared native app fail when performing actions that interact with stages — large result sets, COPY commands (KB 000007862) | The `ENABLE_EXT_CODE_STAGE_ACCESS` account parameter is not enabled. This parameter is required for extension code (Snowpark, Java/Python UDFs) in native apps to access stages. | Contact Snowflake Support to enable stage access for extension code in the consumer's account. This is a Support-managed account parameter — customers cannot enable it themselves. Mention that your Native App uses Snowpark/Java/Python stored procedures that interact with stages. |
| Dynamic Tables owned by a native app fail with error 370001 "Internal Error: Please contact support" and are auto-suspended (KB 000012481) | Dynamic Tables auto-suspend after 5 consecutive non-transient refresh failures (by design, to prevent credit consumption). Once suspended they do NOT resume automatically. | After the underlying platform issue is resolved, manually resume each DT: `ALTER DYNAMIC TABLE <database>.<schema>.<table_name> RESUME;` — then verify with `SHOW DYNAMIC TABLES IN SCHEMA <database>.<schema>;` that `scheduling_state` is ACTIVE. Providers should add monitoring (event tables + alerts) to detect DT failures in consumer accounts. |
