# `ICEBERG_BASE_TABLE_V2_TO_V3`

Per-code handler for the `dynamic-tables-apply-recommendations` skill. The shared handler contract (field definitions, DDL composition rules, and the disclosure of unverified rewrites) lives in [../recommendation-codes.md](../recommendation-codes.md).

- `code`: `ICEBERG_BASE_TABLE_V2_TO_V3`
- `status`: **implemented** (the skill upgrades each V2 base table to V3 in-place using `ALTER ICEBERG TABLE ... UPGRADE TO ICEBERG VERSION 3`)
- `customer_description`: One or more base tables referenced by this dynamic table are Snowflake-managed Iceberg V2 tables. Iceberg V2 has no change tracking, so the DT cannot use per-row change data for incremental refresh and must fall back to a more expensive scan-based approach. Iceberg V3 tables support change tracking, which enables the DT to maintain itself incrementally at lower per-refresh cost.
- `plan_summary`: Upgrade the Iceberg V2 base table(s) listed in `info` to V3 in-place.
- `plan_why`: Iceberg V2 has no change tracking; the DT falls back to full-scan incremental maintenance. Upgrading to V3 enables change tracking, which is expected to reduce refresh cost.
- `detection_signature`: Detected at **create/evolve time** (scope `CREATE_EVOLVE`) — when the DT's query is compiled at `CREATE` or `ALTER`. The recommendation's `info` lists the specific V2 base table(s) by fully-qualified name. This code does **not** re-fire on refreshes; its `lastDetectedAt` is stamped once at compile time and will not advance.
- `ddl_transformation`: in-place Iceberg version upgrade per base table — `ALTER ICEBERG TABLE <table> UPGRADE TO ICEBERG VERSION 3`. No data movement, no temp tables, no name swap. The DT's definition is **unchanged** (it still references the original table name).
- `routes_to_on_manual`: n/a (this code is `implemented`).

---

## ⚠️ REINITIALIZATION

After the upgrade, the DT's base table has new change tracking metadata. **The DT — and any other dynamic tables that read this base table — will perform a `REINITIALIZATION` at their next refresh.** This is expected and cannot be avoided. Disclose this to the customer before executing.

---

## Step 0 — Identify the V2 base table(s) and suspend if needed

Parse the `info` field from the `RECOMMENDATIONS` column. It reads:

> *"One or more base tables are Iceberg V2 tables, which have no change tracking and generally affects refresh performance. Iceberg V2 base tables: `<fully_qualified_table_names>`."*

Extract each fully-qualified table name (e.g. `MY_DB.MY_SCHEMA.MY_TABLE`). Process them in order; all steps below apply to each table.

**If more than one V2 base table is listed**, suspend the DT before beginning the migration loop. This prevents a refresh from firing between upgrades and triggering a partial reinitialization mid-migration:

```sql
ALTER DYNAMIC TABLE <DB>.<SCHEMA>.<DT_NAME> SUSPEND;
```

You will resume the DT in Step 3 after all tables have been upgraded.

---

## Step 1 — Compose and present the upgrade DDL

For each V2 base table, compose the upgrade statement and present it for the customer's approval, along with the REINITIALIZATION disclosure.

```sql
ALTER ICEBERG TABLE <DB>.<SCHEMA>.<V2_TABLE> UPGRADE TO ICEBERG VERSION 3
/* Generated by Snowflake CoCo DT recommendations skill: ICEBERG_BASE_TABLE_V2_TO_V3 */;
```

**Presentation**: show the statement(s) together. Then include:
- The REINITIALIZATION disclosure: *"The dynamic table — and any other dynamic tables that read this base table — will perform a REINITIALIZATION at their next refresh. This is expected since the base table's change tracking was updated."*
- Ask "Want me to run it?"

**Do NOT fold this into a `CREATE OR ALTER DYNAMIC TABLE`** — the DT's definition is unchanged. This is a base-table operation, not DT DDL.

---

## Step 2 — Execute

Execute the `ALTER ICEBERG TABLE ... UPGRADE` statement for each V2 base table. Surface any errors verbatim; do **not** retry on failure.

The `ALTER ICEBERG TABLE ... UPGRADE` statement carries the mandatory CoCo tag.

After all statements succeed, proceed to the Step 3 wrap-up.

---

## Step 3 — Wrap-up

**If the DT was suspended in Step 0**, resume it before wrapping up:

```sql
ALTER DYNAMIC TABLE <DB>.<SCHEMA>.<DT_NAME> RESUME;
```

Use the standard SKILL.md Step 7 template. Include:
- The upgrade is complete; `<V2_TABLE>` is now an Iceberg V3 table.
- The DT definition is unchanged — it still references the same table name.
- The DT will perform a **`REINITIALIZATION`** at its next refresh (restate, don't newly introduce).
- **Verbatim:** *"may take time to update"* (RECOMMENDATIONS column caveat).
- **Verbatim:** *"running the dynamic table further"* and *"monitor refresh times"*.
- The post-change monitoring query from SKILL.md Step 7.
