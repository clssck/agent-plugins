# `WAREHOUSE_TOO_SMALL` (synthetic)

Synthetic recommendation generated by the `dynamic-tables-apply-recommendations` skill after processing all INFORMATION_SCHEMA-emitted codes. **Not** emitted by Snowflake's recommendations engine — detected by the skill via refresh history and query spilling data.

- `code`: `WAREHOUSE_TOO_SMALL` (synthetic)
- `status`: **implemented** (if the customer accepts, the skill applies the warehouse change)
- `customer_description`: The dynamic table's recent refresh queries have been spilling to disk, and those spilling refreshes take noticeably longer than non-spilling ones — a sign the warehouse is undersized for the DT's working-set memory. Spill to **local** storage (`bytes_spilled_to_local_storage`) is the primary signal; spill to **remote** storage (`bytes_spilled_to_remote_storage`) also counts, **except when the query acceleration service (QAS) is enabled** on the warehouse — QAS writes a small amount to remote storage for every eligible query, so under QAS a nonzero remote spill is expected bookkeeping and is ignored (see Step 3). Increasing the warehouse size by one tier removes spill overhead and can reduce refresh times.
- `plan_summary`: Upsize the refresh warehouse by one tier.
- `plan_why`: Recent refreshes are spilling to disk and running noticeably slower because of it.

## Step 1 — Get the DT's current warehouses and their sizes

```sql
SHOW DYNAMIC TABLES LIKE '<DT>' IN SCHEMA <DB>.<SCHEMA>;
SELECT "name", "warehouse", "initialization_warehouse"
FROM TABLE(RESULT_SCAN(LAST_QUERY_ID()))
WHERE UPPER("name") = UPPER('<DT>');
```

Record `<CURRENT_WH>` (the `warehouse` column) and `<CURRENT_INIT_WH>` (the `initialization_warehouse` column — `NULL` if not set). Then determine the tier of each:

```sql
SHOW WAREHOUSES LIKE '<CURRENT_WH>';
SELECT "name", "size" AS warehouse_size, "enable_query_acceleration"
FROM TABLE(RESULT_SCAN(LAST_QUERY_ID()));
```

Record the tier and whether the query acceleration service (QAS) is enabled: `<CURRENT_WH_QAS>` = the `enable_query_acceleration` value (`true`/`false`). QAS enablement changes how remote-storage spill is interpreted in Step 3.

If `<CURRENT_INIT_WH>` is set (not NULL), also run:

```sql
SHOW WAREHOUSES LIKE '<CURRENT_INIT_WH>';
SELECT "name", "size" AS warehouse_size, "enable_query_acceleration"
FROM TABLE(RESULT_SCAN(LAST_QUERY_ID()));
```

Record `<CURRENT_INIT_WH_QAS>` the same way.

## Step 2 — Fetch representative refreshes with spilling data

Fetch the last 20 SUCCEEDED non-NO_DATA refreshes within the past 7 days (whichever bound is reached first), joined to query-level spilling metrics.

**Primary — `INFORMATION_SCHEMA.QUERY_HISTORY_BY_WAREHOUSE()` (real-time, requires MONITOR or OPERATE on `<CURRENT_WH>`):**

```sql
WITH recent_refreshes AS (
    SELECT
        query_id,
        refresh_action,
        refresh_start_time,
        DATEDIFF('second', refresh_start_time, refresh_end_time) AS duration_sec
    FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY(
        NAME => '<DB>.<SCHEMA>.<DT>'
    ))
    WHERE state          = 'SUCCEEDED'
      AND refresh_action != 'NO_DATA'
      AND refresh_start_time >= DATEADD('day', -7, CURRENT_TIMESTAMP())
    ORDER BY refresh_start_time DESC
    LIMIT 20
)
SELECT
    r.query_id,
    r.refresh_action,
    r.duration_sec,
    COALESCE(q.bytes_spilled_to_local_storage,  0)                                                   AS bytes_spilled_local,
    COALESCE(q.bytes_spilled_to_remote_storage, 0)                                                   AS bytes_spilled_remote,
    COALESCE(q.bytes_spilled_to_local_storage,  0) +
    COALESCE(q.bytes_spilled_to_remote_storage, 0)                                                   AS total_bytes_spilled
FROM recent_refreshes r
LEFT JOIN TABLE(INFORMATION_SCHEMA.QUERY_HISTORY_BY_WAREHOUSE(
    WAREHOUSE_NAME       => '<CURRENT_WH>',
    DATA_TIMESTAMP_START => DATEADD('day', -7, CURRENT_TIMESTAMP()),
    DATA_TIMESTAMP_END   => DATEADD('minute', 5, CURRENT_TIMESTAMP())
)) q ON r.query_id = q.query_id
ORDER BY r.refresh_start_time DESC;
```

**Fallback — `SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY` (up to 45-min latency; requires IMPORTED PRIVILEGES on the SNOWFLAKE database):**

```sql
WITH recent_refreshes AS (
    SELECT
        query_id,
        refresh_action,
        DATEDIFF('second', refresh_start_time, refresh_end_time) AS duration_sec
    FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY(
        NAME => '<DB>.<SCHEMA>.<DT>'
    ))
    WHERE state          = 'SUCCEEDED'
      AND refresh_action != 'NO_DATA'
      AND refresh_start_time >= DATEADD('day', -7, CURRENT_TIMESTAMP())
    ORDER BY refresh_start_time DESC
    LIMIT 20
)
SELECT
    r.query_id,
    r.refresh_action,
    r.duration_sec,
    COALESCE(q.bytes_spilled_to_local_storage,  0)  AS bytes_spilled_local,
    COALESCE(q.bytes_spilled_to_remote_storage, 0)  AS bytes_spilled_remote,
    COALESCE(q.bytes_spilled_to_local_storage,  0) +
    COALESCE(q.bytes_spilled_to_remote_storage, 0)  AS total_bytes_spilled
FROM recent_refreshes r
LEFT JOIN SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY q ON r.query_id = q.query_id;
```

If neither source is accessible (privilege error on both), **skip this check entirely** — do not present the recommendation.

## Step 3 — Interpret the results

Separate the representative refreshes into two groups by `refresh_action`:
- **Incremental/full refreshes**: `refresh_action IN ('INCREMENTAL', 'FULL')` — these always use `<CURRENT_WH>`.
- **Reinitializations**: `refresh_action = 'REINITIALIZATION'` — these use `<CURRENT_INIT_WH>` if set, otherwise fall back to `<CURRENT_WH>`.

**What counts as a memory-pressure spill (QAS caveat).** Use **local**-storage spill as the signal, not the local+remote total. A refresh is a **spilling refresh** when:

- `bytes_spilled_local > 0`, **or**
- `bytes_spilled_remote > 0` **and** QAS is **not** enabled on the warehouse that ran it — `<CURRENT_WH_QAS>` for incremental/full refreshes; `<CURRENT_INIT_WH_QAS>` (or `<CURRENT_WH_QAS>` when no initialization warehouse is set) for reinitializations.

When QAS is enabled, Snowflake writes a small amount of data to remote storage for **every eligible query even if QAS isn't actually used for it**, so a nonzero `bytes_spilled_to_remote_storage` under QAS is expected bookkeeping — **not** a memory-pressure signal — and must be ignored. Local-storage spill is unaffected by QAS and remains the reliable indicator that the warehouse is undersized. See <https://docs.snowflake.com/en/user-guide/performance-query-warehouse-memory> (the "Tip": don't be concerned by a nonzero `bytes_spilled_to_remote_storage` when QAS is enabled). Treating remote spill as a trigger while QAS is on is a false positive — do not do it.

For each group, determine whether it "spills" — **both** conditions must hold:

1. **At least 3 refreshes in the group are spilling refreshes** (per the definition above) — spilling is frequent, not a one-off.
2. **Spilling refreshes in the group are noticeably slower than non-spilling ones** — heuristic: `avg_duration_spilling_sec > avg_duration_non_spilling_sec * 1.2`. If all refreshes in the group spilled (no non-spilling baseline), condition 2 is satisfied by default.

Then apply this decision tree:

| Incremental/full spills? | Reinitializations spill? | `INITIALIZATION_WAREHOUSE` set? | Action |
|---|---|---|---|
| ✅ Yes | ❌ No | — | Upgrade `WAREHOUSE` by one tier |
| ❌ No | ✅ Yes | ✅ Yes | Upgrade `INITIALIZATION_WAREHOUSE` by one tier |
| ❌ No | ✅ Yes | ❌ No | Recommend setting `INITIALIZATION_WAREHOUSE` to one tier above current `WAREHOUSE` size |
| ✅ Yes | ✅ Yes | — | Upgrade `WAREHOUSE` by one tier (it controls both kinds of refreshes) |
| ❌ No | ❌ No | — | Skip — do not present the recommendation |

If there are no reinitialization refreshes in the history window, treat the "reinitializations spill?" column as ❌ No.

## Step 4 — Determine how to surface this finding

- **DEFERRED** (surface as context only, do not offer as an actionable option now): other INFORMATION_SCHEMA codes with `status: implemented` are also present and have real DDL changes to apply. **Do not** add `WAREHOUSE_TOO_SMALL` to the selectable recommendation list. Instead, surface the spilling finding as context alongside the other recommendations — explain that disk spilling was detected, but **strongly recommend that the customer apply the other recommendations first, monitor refresh performance over the next several cycles, and only revisit the warehouse size if spilling persists afterward**. Those other fixes directly reduce the DT's refresh cost and may eliminate spilling as a side effect. Frame this as: *"Your dynamic table is also spilling data to disk on recent refreshes. I'd apply the other recommendations first — they directly reduce refresh cost and may resolve the spilling as a side effect. Once the dynamic table has run for a few cycles under the new settings, check whether spilling persists. If it does, upgrading the warehouse would be the next step."*
- **STRONGLY RECOMMENDED** (present as the primary actionable recommendation): no other actionable INFORMATION_SCHEMA codes exist, OR all other codes are `manual` / informational with no clear DDL fix (e.g. `EXPENSIVE_ORDER_DEPENDENT_WINDOW_FUNCTION`, `NON_MONOTONIC_GROUPING_KEY`, `AUTO_RESOLVED_TO_FULL_REFRESH`). In these cases, upsizing the warehouse is the most direct available lever.

## Step 5 — Warehouse size progression

Recommend upgrading exactly **one tier** up the Snowflake warehouse size ladder:

```
X-Small → Small → Medium → Large → X-Large → 2X-Large → 3X-Large → 4X-Large → 5X-Large → 6X-Large
```

Determine `<REQUIRED_SIZE>` = the next tier above `<CURRENT_WH>`'s size. If the DT is already on 6X-Large, the warehouse cannot be upsized further — say so and skip the recommendation.

Note: Snowflake's `SHOW WAREHOUSES` uses the `size` column values `'X-Small'`, `'Small'`, `'Medium'`, `'Large'`, `'X-Large'`, `'2X-Large'`, etc. When creating a warehouse, use the `WAREHOUSE_SIZE = XSMALL` / `SMALL` / `MEDIUM` ... form (no hyphen).

#### Case A — Upgrading `WAREHOUSE` and other INFORMATION_SCHEMA DDL is also being composed

Fold the warehouse change into the existing `CREATE OR ALTER DYNAMIC TABLE` statement by updating the `WAREHOUSE` clause. Do **not** emit a separate `ALTER DYNAMIC TABLE SET WAREHOUSE` — a single `CREATE OR ALTER` avoids two reinitializations.
