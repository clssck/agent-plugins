# Alert Action-Level Muting (Throttle)

Use this pattern when an alert should evaluate normally (`TRIGGERED` when condition matches) but notification delivery must be rate-limited (for example, at most once per hour).

## Goal

- Keep failure detection logic in the `IF` condition only.
- Keep mute/throttle logic in the `THEN` action.
- Avoid extra helper objects unless explicitly requested.

## Required Objects

Create a tracking table in the same schema as the alert:

```sql
CREATE TABLE IF NOT EXISTS NOTIFICATION_TRACKING (
  last_notification_time TIMESTAMP_NTZ
);
```

## Action-Level Mute Pattern

Inside the alert action:

1. Read the latest `last_notification_time`.
2. Convert the current time to UTC (`TIMESTAMP_NTZ`) before time arithmetic.
3. Determine whether enough time has passed (for hourly mute, 60 minutes / 3600 seconds).
4. Only send notification when allowed.
5. Update tracking table after a send using UTC timestamp.

## Action Block Template (inside alert action)

```sql
BEGIN
  LET current_utc TIMESTAMP_NTZ := CONVERT_TIMEZONE('UTC', CURRENT_TIMESTAMP())::TIMESTAMP_NTZ;

  LET should_send BOOLEAN := (
    SELECT COALESCE(MAX(last_notification_time), '1970-01-01'::TIMESTAMP_NTZ)
           < DATEADD('hour', -<mute_interval_hours>, :current_utc)
    FROM <tracking_table>
  );

  IF (should_send) THEN
    CALL SYSTEM$SEND_SNOWFLAKE_NOTIFICATION(
      <notification_content_varchar>,
      '<integration_config_json>'
    );

    MERGE INTO <tracking_table> t
    USING (SELECT :current_utc AS ts) s
    ON 1=1
    WHEN MATCHED THEN UPDATE SET last_notification_time = s.ts
    WHEN NOT MATCHED THEN INSERT (last_notification_time) VALUES (s.ts);
  END IF;
END;
```

## Scheduled Alert Template with Action-Level Mute

Use this when you want continuous detection in the condition and throttled notifications in the action.


```sql
CREATE TABLE IF NOT EXISTS <tracking_table> (
  last_notification_time TIMESTAMP_NTZ
);

CREATE OR REPLACE ALERT <alert_name>
  SCHEDULE = '<schedule_interval>'
  IF (EXISTS (
    <condition_query>
  ))
  THEN
    BEGIN
      LET current_utc TIMESTAMP_NTZ := CONVERT_TIMEZONE('UTC', CURRENT_TIMESTAMP())::TIMESTAMP_NTZ;
      LET should_send BOOLEAN := (
        SELECT COALESCE(MAX(last_notification_time), '1970-01-01'::TIMESTAMP_NTZ)
               < DATEADD('hour', -<mute_interval_hours>, :current_utc)
        FROM <tracking_table>
      );

      IF (should_send) THEN
        CALL SYSTEM$SEND_SNOWFLAKE_NOTIFICATION(
          <notification_content_varchar>,
          '<integration_config_json>'
        );

        MERGE INTO <tracking_table> t
        USING (SELECT :current_utc AS ts) s
        ON 1=1
        WHEN MATCHED THEN UPDATE SET last_notification_time = s.ts
        WHEN NOT MATCHED THEN INSERT (last_notification_time) VALUES (s.ts);
      END IF;
    END;
```

## Parameters

| Parameter | Description |
|-----------|-------------|
| `<tracking_table>` | Tracking table name in the alert schema (for example, `NOTIFICATION_TRACKING`) |
| `<alert_name>` | Alert name |
| `<schedule_interval>` | Alert schedule (for example, `'1 MINUTE'`, `'5 MINUTE'`) |
| `<condition_query>` | Detection query that should remain continuous and unthrottled |
| `<mute_interval_hours>` | Notification throttle window in hours (for once per hour, use `1`) |
| `<notification_content_varchar>` | Content generated by `notification-content/SKILL.md` (for example, `SNOWFLAKE.NOTIFICATION.TEXT_HTML(...)` or `SNOWFLAKE.NOTIFICATION.APPLICATION_JSON(...)`) |
| `<integration_config_json>` | Integration config JSON string for `SYSTEM$SEND_SNOWFLAKE_NOTIFICATION` second argument (for example, `'{"my_webhook_int": {}}'` or `'{"my_email_int": {"subject": "Alert", "toAddress": ["user@example.com"]}}'`) |

## Avoid

- Putting mute predicates in the alert `IF` condition (this turns expected `TRIGGERED` runs into `CONDITION_FALSE`).
- Creating extra procedures/tasks/functions for simple throttle requirements.
- Using dynamic SQL (`EXECUTE IMMEDIATE`) when a direct alert definition is sufficient.
