# Contributing

Maintainer documentation for this repository. The [README](./README.md) is a generated catalog.

## Maintenance

[`.github/workflows/sync-upstreams.yml`](./.github/workflows/sync-upstreams.yml) runs [`scripts/sync.ts`](./scripts/sync.ts) daily at 06:17 UTC and on manual dispatch. It pins and fetches upstreams, regenerates the catalog, and runs every gate below in a read-only job. Nothing is pushed to `main`: when the gates pass and files changed, a separate job with write access applies the patch to the `automation/sync-upstreams` branch (rebuilt from the current `main` and force-updated only while its remote lease still matches) and opens or refreshes the one pull request for it. A human reviews and merges that PR; upstream content is data to review, never trusted. A run with no changes closes a stale sync PR. Pushes to `main` that touch sync inputs run the same read-only job and publish nothing. The repository setting "Allow GitHub Actions to create and approve pull requests" MUST be enabled for the publish job to open the PR.

Gates ([`.github/actions/gates`](./.github/actions/gates/action.yml), shared by Validate and Sync):

| Gate | Command | Proves |
|---|---|---|
| Root install | `bun install --frozen-lockfile` | Dependencies match `bun.lock` |
| Bun tests | `bun test scripts` | Sync, compatibility, rule, and README behavior |
| Python helpers | `uv run --no-project python -B -m unittest discover -p 'test_*.py'` in each of `packs/sanofi/skills/{iac-terraform,datacontract-writing,adr-writing,confluence-html-editor}/scripts` | First-party helper scripts work |
| Static repository check | `bun scripts/sync.ts --check` | Declared skills, rules, agents, commands, and tools are discoverable; compatibility output is current; concrete `skill://` targets resolve; skill names are unambiguous; every generated `upstream/<name>` tree matches its digest. It does not run OMP and does not execute a skill workflow |
| OMP host-loader smoke | `OMP_ROOT=… bun scripts/check-omp-loader.ts` | OMP's own providers, task-agent parser, and extension loader accept every pack, at the `reviewedCommit` in [`omp-source-lock.json`](./omp-source-lock.json) with the `natives` addon pinned there by tarball integrity (`bun install --frozen-lockfile` in the checkout) |

A pull request opened with `github.token` does not trigger Validate, which is why Sync runs the gates before proposing anything. Close and reopen the PR to run Validate on it. Every GitHub Action reference is pinned to a full commit SHA with a version comment, and Dependabot proposes weekly bumps for both; the Bun (`1.4.3`) and uv (`0.13.1`) versions are inputs in the gates action and change by hand. When the lock's `reviewedCommit` moves to a release with a different `@oh-my-pi/pi-natives` version, update `natives.version` and `natives.integrity` with it (`npm view @oh-my-pi/pi-natives-linux-x64@<version> dist.integrity`).

The README is regenerated by the sync run, so a local run leaves it alone. To update it locally: `GITHUB_TOKEN=$(gh auth token) bun scripts/sync.ts --readme`. `bun scripts/sync.ts --local` runs the static repository check without network access or a token; it never loads OMP, so a pass means the repository contract holds, not that OMP loaded the packs.

Local development uses the shared default plugin store: run `bun install --cwd ~/Projects/agent-plugins`, then `omp plugin link ~/Projects/agent-plugins/packs/clssck-core` (and `packs/clssck-development` when working on it) to make working-tree edits live in normal sessions. OMP profiles do not isolate plugin links. Re-link the installed-copy path shown in the README to return to release behavior.

## CoCo compatibility (`coco@2`)

Packs in CoCo format are adapted by [`scripts/compatibility.ts`](./scripts/compatibility.ts), versioned by `COMPATIBILITY_VERSION` (currently 2). Generated upstreams opt in with `"compatibility": "coco"` in `sources.json`; committed `packs/coco-*` opt in with `ompCompatibility.profile` in their `package.json`. The layer is deterministic and runs only on copies in this repository; source repositories are never modified, so packaged text may differ from the original beyond link syntax.

- CoCo question aliases (`AskUserQuestion`, `ask_user_question`, `ask_question`, `multiSelect`) become OMP `ask` calls with `questions[]`, an intent, stable unique ids, object options, and OMP-native recommendation/`Other` semantics. Approval gates require an explicit user response.
- Known delegation shapes become OMP `task` batches; legacy task fields, implicit question payloads, unsupported `skill()` calls, and non-OMP todo names fail compatibility lint instead of shipping silently.
- `skill()`, `$skill-name`, and web-fetch aliases become OMP `skill://`/`read` instructions. External capabilities such as the `cortex agent-studio` CLI, `nipyapi`, `snowflake.connector`, and Snowflake-only tools receive an availability/authentication gate and must stop as blocked when absent; the adapter never invents a shell fallback.
- Missing Markdown references are repaired or de-linked. Concrete `skill://` roots and subpaths must resolve within the same pack or through a declared `ompSkillReferences.requires` provider; only targets declared in that pack's `ompSkillReferences.optional` list may be absent.
- `cortex-code-guide` is a product reference for Cortex Code itself, so its descriptions of Cortex Code tool names are preserved and excluded from OMP-instruction aliasing.
- `bun scripts/sync.ts --check` is read-only. Generated `package.json` records `ompCompatibility` (`profile`, `version`) and pinned `sync` provenance; checks reject stale output or mismatched metadata. `--local` checks packages without network access and does not rewrite committed CoCo packs. After editing the adapter, run `bun scripts/compatibility.ts --write packs/<pack>` for each affected committed pack; normal network sync rebuilds opted-in generated upstreams.

## Generated tree integrity

Everything under `upstream/<name>/` is generated; never edit it by hand. Fetch records `sync.tree` in each generated `package.json`: a SHA-256 over every file's POSIX path, executable bit, and content hash in sorted order, with `package.json` hashed in its generated form minus `sync.tree` itself (the only excluded value). Integrity reads are streamed and reject any individual generated file over 16 MiB. `bun scripts/sync.ts --check` recomputes the digest and fails on any edited, added, or removed file, a changed executable bit, a hand-formatted manifest, or a missing or forged digest. Fetch and the check also reject symlinks and other non-regular entries inside a generated tree, so a symlink in an upstream fails the build instead of shipping. A hand edit is repaired by the next sync, which rebuilds any tree that fails the check. To change generated content, change `sources.json` or the adapter and re-sync.

## Add an upstream

Append to `upstreams` in `sources.json`: `name` (the pack name), `repo` (`owner/name`), `ref` (branch), `sha` (any commit; the sync moves it), `description`, and `include`, which maps upstream paths to pack paths (usually `{ "skills": "skills" }`). Merge to `main`; the next sync run opens a PR with the generated pack.

## Add a pack of your own

Create `packs/<name>/package.json` with `name` (matching the directory), `version`, and `"omp": {}` (list TypeScript extension modules under `omp.extensions`). Add `skills/<skill>/SKILL.md`, `agents/*.md`, or `commands/*.md` as needed; OMP does not look inside subdirectories of `rules/`, `agents/`, or `commands/`.

## `clssck-development`

`packs/clssck-development/` is a first-party, repository-agnostic pack maintained here. It began from MIT-licensed `can1357/oh-my-pi` development assets, recorded in [`licenses/clssck-development/`](./licenses/clssck-development/ATTRIBUTION). Edit it in place, keep tool dependencies in the root `package.json`, and bump the pack version when behavior changes. It is never synced from OMP: [`omp-source-lock.json`](./omp-source-lock.json) pins the reviewed OMP `.omp/commands`, `.omp/skills`, and `.omp/tools` trees, and the Sync workflow runs `scripts/check-omp-source.ts --notify` to open one assigned issue when they change. After reviewing and adapting that diff by hand, update the lock to the reviewed commit and trees (and the `natives` pin, per above); CI then runs the host-loader smoke against that commit.

Run the host-loader smoke locally, offline, with any oh-my-pi checkout that has a built native addon: `OMP_ROOT=/path/to/oh-my-pi bun scripts/check-omp-loader.ts`. It runs every pack through the OMP providers, task-agent parser, and extension loader, then the packaged builtin prompt probe via `--show`. Also run `bun scripts/sync.ts --check`.

## Rules

Edit rules directly in `packs/<pack>/rules/`; this is the path OMP discovers and the single source of truth. Keep every rule self-contained because OMP does not expand imports or fragments. Rule fields live in `omp://ttsr-injection-lifecycle.md`; discovery and matching semantics in `omp://rulebook-matching-pipeline.md`. Use the bundled rules in `packages/coding-agent/src/discovery/builtin-rules/*.md` as the semantic baseline: `description`, `condition`, `scope`, and `interruptMode` frontmatter, with the filename as the rule name. OMP injects the Markdown body verbatim.

## Authored style

Skills written here follow OMP's project-skill semantics as the host contract. Canonical authored prompt guidance lives in `packs/clssck-development/skills/` (`system-prompts`, `tool-prompt-optimization`, `semantic-compression`); `omp://skills.md` defines discovery, layout, and runtime frontmatter. Use `name` plus a trigger-rich `description`. A skill that must remain slash-triggerable but hidden from automatic model invocation uses `disable-model-invocation: true` (OMP extension frontmatter — omit it from standard `plugin.json` packages; strict validation rejects unknown fields); do not add alternate discovery symlinks. Optimize descriptions for retrieval coverage, not a fixed word count. Use task headings for procedures, noun headings for reference material, tables for real enumerations, and executable examples where behavior depends on exact syntax.

Agents and rules use the same dense, imperative voice, not an identical heading template. Agent prompts take role, RFC 2119, and critical-edge guidance from `system-prompts`; bundled prompts under `packages/coding-agent/src/prompts/agents/` and `omp://task-agent-discovery.md` define their actual fields and discovery contract.

## Licensing

Third-party license texts and attributions live in [`licenses/`](./licenses/README.md), never inside a skill directory: a skill folder holds only what the skill loads at runtime. When a skill adapts third-party material, add its license or attribution under `licenses/` and a row to that folder's README. The root [`LICENSE`](./LICENSE) covers what is written here; vendored packs and `upstream/` copies stay under the terms their own files state.
