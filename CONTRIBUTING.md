# Contributing

Maintainer documentation for this repository. The [README](./README.md) is a generated catalog.

## Maintenance

[`.github/workflows/sync-upstreams.yml`](./.github/workflows/sync-upstreams.yml) runs [`scripts/sync.ts`](./scripts/sync.ts) daily at 06:17 UTC, on manual dispatch, and on pushes to `main` that touch sync inputs. It pins and fetches upstreams, regenerates the catalog, and runs every gate below in a read-only job. When the gates pass and files changed, a separate job with write access applies the validated patch to the run's exact base commit and pushes directly to `main`; no pull request is created. Publication uses a normal fast-forward push, never force or an untested rebase. If `main` changes during validation, publication fails and Sync must run again against the new base. Retrying an already published tree succeeds without another push. A run with no changes publishes nothing. Upstream content remains third-party instructions: these gates establish structural compatibility and tested behavior, not the quality of every instruction. Repository rules must permit this Actions token to push to `main`.

Gates ([`.github/actions/gates`](./.github/actions/gates/action.yml), shared by Validate and Sync):

| Gate | Command | Proves |
|---|---|---|
| Root install | `bun install --frozen-lockfile` | Root manifest installs cleanly; currently no root dependencies |
| Bun tests | `bun test scripts` | Sync, rule, and README behavior |
| Python helpers | `uv run --no-project python -B -m unittest discover -p 'test_*.py'` in each of `packs/sanofi/skills/{iac-terraform,datacontract-writing,adr-writing,confluence-html-editor}/scripts` | First-party helper scripts work |
| Static repository check | `bun scripts/sync.ts --check` | Declared skills, rules, agents, commands, and tools are discoverable; concrete `skill://` targets resolve; skill names are unambiguous; every generated `upstream/<name>` tree matches its digest. It does not run OMP and does not execute a skill workflow |
| OMP host-loader smoke | `OMP_ROOT=… bun scripts/check-omp-loader.ts` | OMP's own providers, task-agent parser, and extension loader accept every pack, at the `reviewedCommit` in [`omp-source-lock.json`](./omp-source-lock.json) with the `natives` addon pinned there by tarball integrity (`bun install --frozen-lockfile` in the checkout) |

A push made with `github.token` does not trigger Validate or another Sync run, which is why Sync runs all gates before publishing. This also prevents a recursive sync loop. Every GitHub Action reference is pinned to a full commit SHA with a version comment, and Dependabot proposes weekly bumps for both; the Bun (`1.4.3`) and uv (`0.13.1`) versions are inputs in the gates action and change by hand. When the lock's `reviewedCommit` moves to a release with a different `@oh-my-pi/pi-natives` version, update `natives.version` and `natives.integrity` with it (`npm view @oh-my-pi/pi-natives-linux-x64@<version> dist.integrity`).

The README is regenerated by the sync run, so a local run leaves it alone. To update it locally: `GITHUB_TOKEN=$(gh auth token) bun scripts/sync.ts --readme`. `bun scripts/sync.ts --local` runs the static repository check without network access or a token; it never loads OMP, so a pass means the repository contract holds, not that OMP loaded the packs.

Local development uses the shared default plugin store: run `bun install --cwd ~/Projects/agent-plugins`, then `omp plugin link ~/Projects/agent-plugins/packs/clssck` to make working-tree edits live in normal sessions. OMP profiles do not isolate plugin links. Re-link the installed-copy path shown in the README to return to release behavior.

## Generated tree integrity

Everything under `upstream/<name>/` is generated; never edit it by hand. Fetch records `sync.tree` in each generated `package.json`: a SHA-256 over every file's POSIX path, executable bit, and content hash in sorted order, with `package.json` hashed in its generated form minus `sync.tree` itself (the only excluded value). Integrity reads are streamed and reject any individual generated file over 16 MiB. `bun scripts/sync.ts --check` recomputes the digest and fails on any edited, added, or removed file, a changed executable bit, a hand-formatted manifest, or a missing or forged digest. Fetch and the check also reject symlinks and other non-regular entries inside a generated tree, so a symlink in an upstream fails the build instead of shipping. A hand edit is repaired by the next sync, which rebuilds any tree that fails the check. To change generated content, change `sources.json` or the adapter and re-sync.

## Add an upstream

Append to `upstreams` in `sources.json`: `name` (the pack name), `repo` (`owner/name`), `ref` (branch), `sha` (any commit; the sync moves it), `description`, and `include`, which maps upstream paths to pack paths (usually `{ "skills": "skills" }`). Merge to `main`; the next successful sync publishes the generated pack to `main`.

## Add a pack of your own

Create `packs/<name>/package.json` with `name` (matching the directory), `version`, and `"omp": {}` (list TypeScript extension modules under `omp.extensions`). Add `skills/<skill>/SKILL.md`, `agents/*.md`, or `commands/*.md` as needed; OMP does not look inside subdirectories of `rules/`, `agents/`, or `commands/`.

## Vendored upstream skills

Some first-party skills began as copies of an upstream repository and are edited here from then on. `packs/clssck/skills` holds the Emil Kowalski design skills (`emilkowalski/skills`, attribution under [`licenses/emilkowalski-skills/`](./licenses/emilkowalski-skills)). They are intentionally not in `sources.json`, so the daily sync never regenerates or overwrites them. [`upstream-watch.json`](./upstream-watch.json) records each watched upstream instead: `repository`, `ref`, `path`, the `reviewedCommit` last ported, the vendored `target`, and the `issueTitle`.

The flow is watch → issue → PR. The `upstream-watch` job in the Sync workflow runs [`scripts/check-upstream-watch.ts`](./scripts/check-upstream-watch.ts) `--notify`, which asks GitHub for the latest commit touching `ref:path` and compares it with the path's state at `reviewedCommit`. A difference opens (or refreshes) one issue per source, assigned to the maintainer, with the compare URL, the pinned and latest commits, and the target path. A matching pin closes the issue. Review the upstream diff, port what is useful into the target in a pull request (the usual gates apply), and in that PR update `reviewedCommit` to the newest upstream commit reviewed. Merging it closes the issue on the next run. To add a watch, append an entry to `sources` in `upstream-watch.json`. Locally, `GITHUB_TOKEN=$(gh auth token) bun scripts/check-upstream-watch.ts` prints changed sources and exits 1 without writing anything.

## `clssck`

`packs/clssck/` is the first-party pack maintained here: skills, rules, agents, and generalized repository commands. Its commands began from MIT-licensed `can1357/oh-my-pi` command templates, recorded in [`licenses/clssck/commands/`](./licenses/clssck/commands/ATTRIBUTION). Edit it in place and bump the pack version when behavior changes. It is never synced from OMP: [`omp-source-lock.json`](./omp-source-lock.json) pins the reviewed `.omp/commands` tree, and the Sync workflow runs `scripts/check-omp-source.ts --notify` to open one assigned issue when it changes. After reviewing and adapting that diff by hand, update the lock to the reviewed commit and tree (and the `natives` pin, per above); CI then validates the repository contract.

Run the host-loader smoke locally, offline, with any oh-my-pi checkout that has a built native addon: `OMP_ROOT=/path/to/oh-my-pi bun scripts/check-omp-loader.ts`. It runs every pack through the OMP providers, task-agent parser, extension loader, and custom-tool factories, then tests SQL rules with direct connector arguments through OMP's TTSR manager and verifies manual-only skill discovery. These are deterministic host-contract checks, not model-quality evaluations.

## Rules

Edit rules directly in `packs/<pack>/rules/`; this is the path OMP discovers and the single source of truth. Keep every rule self-contained because OMP does not expand imports or fragments. Rule fields live in `omp://ttsr-injection-lifecycle.md`; discovery and matching semantics in `omp://rulebook-matching-pipeline.md`. Use the bundled rules in `packages/coding-agent/src/discovery/builtin-rules/*.md` as the semantic baseline: `description`, `condition`, `scope`, and `interruptMode` frontmatter, with the filename as the rule name. OMP injects the Markdown body verbatim.

## Authored style

Skills written here follow OMP's project-skill semantics as the host contract. Use the actual bundled workflows, agent prompts, and tool descriptions at the reviewed OMP commit as the primary structural and semantic reference; retain repository-specific requirements without introducing another workflow framework. Skill structure and authoring guidance lives in `packs/clssck/skills/skill-authoring/`; `omp://skills.md` defines discovery, layout, and runtime frontmatter. Use `name` plus a trigger-rich `description`. A skill that must remain slash-triggerable but hidden from automatic model invocation uses `disable-model-invocation: true` (OMP extension frontmatter — omit it from standard `plugin.json` packages; strict validation rejects unknown fields); do not add alternate discovery symlinks. Optimize descriptions for retrieval coverage, not a fixed word count. Use task headings for procedures, noun headings for reference material, tables for real enumerations, and executable examples where behavior depends on exact syntax.

Agents and rules use the same dense, imperative voice, not an identical heading template. Agent prompts take role, RFC 2119, and critical-edge guidance from the bundled prompts under `packages/coding-agent/src/prompts/agents/`; `omp://task-agent-discovery.md` defines their actual fields and discovery contract.

## Licensing

Third-party license texts and attributions live in [`licenses/`](./licenses/README.md), never inside a skill directory: a skill folder holds only what the skill loads at runtime. When a skill adapts third-party material, add its license or attribution under `licenses/` and a row to that folder's README. The root [`LICENSE`](./LICENSE) covers what is written here; vendored packs and `upstream/` copies stay under the terms their own files state.
