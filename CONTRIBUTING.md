# Contributing

Maintainer documentation for this repository. The [README](./README.md) is a generated catalog.

## Maintenance

[`.github/workflows/sync-upstreams.yml`](./.github/workflows/sync-upstreams.yml) runs [`scripts/sync.ts`](./scripts/sync.ts) daily at 06:17 UTC and on pushes that change `packs/`, `rule-sources/`, `sources.json`, or `scripts/`. It moves every upstream in [`sources.json`](./sources.json) to the latest commit of its branch, copies it into `upstream/`, regenerates the README, and commits the result. The run fails, and commits nothing, if any skill, rule, agent, or command would not load in OMP, two packs define the same skill, or a generated rule is out of date with its source. That check covers only loadability and names; it does not run or verify any skill's workflow.

The README is regenerated by the workflow on every run, so a local run leaves it alone. To update it locally: `GITHUB_TOKEN=$(gh auth token) bun scripts/sync.ts --readme`. `bun scripts/sync.ts --local` renders rules and runs the load check without network access or a token.

## Add an upstream

Append to `upstreams` in `sources.json`: `name` (the pack name), `repo` (`owner/name`), `ref` (branch), `sha` (any commit; the sync moves it), `description`, and `include`, which maps upstream paths to pack paths (usually `{ "skills": "skills" }`). Push, and the workflow does the rest.

## Add a pack of your own

Create `packs/<name>/package.json` with `name` (matching the directory), `version`, and `"omp": {}` (list TypeScript extension modules under `omp.extensions`). Add `skills/<skill>/SKILL.md`, `agents/*.md`, or `commands/*.md` as needed; OMP does not look inside subdirectories of `rules/`, `agents/`, or `commands/`.

## Rules

`packs/<pack>/rules/` is generated: edit `rule-sources/<pack>/*.md`, then run `bun scripts/sync.ts --local` and commit both. Shared regex fragments live in `rule-sources/fragments/<name>.regex` and are referenced in a rule's frontmatter as `{{<name>}}`; `shell-command-start` and `json-command-start` match the start of a shell command in raw and JSON-encoded tool arguments. A rule in `packs/<pack>/rules/` without a source fails the check. Rule fields, scopes, and matching semantics: `omp://rulebook-matching-pipeline.md`; trigger and injection behavior: `omp://ttsr-injection-lifecycle.md`. The rule name is the filename; a repository rule keeps `description`, `condition`, `scope`, and `interruptMode` only.

## Authored style

Skills written here follow OMP's bundled house style — read `system-prompts`, `tool-prompt-optimization`, and `semantic-compression` in the OMP repository (`oh-my-pi/.omp/skills/`) before writing one, and `omp://skills.md` for discovery, layout, and frontmatter requirements. Frontmatter is `name` and `description` only (`disable-model-invocation` keeps a skill manual-only). The body is a `# Title`, a dense intro paragraph, then `##` topic sections whose rules carry bold lead-ins, with tables for enumerations and real commands instead of abstract description. The description is retrieval surface: 40-70 words, trigger-rich, phrased "Use when …", keeping sibling boundaries — the model sees only it before choosing a skill. Keep `SKILL.md` a router of about 150 lines or fewer and put detail in reference files behind relative links. Telegraphic, no-hedge prose; RFC 2119 keywords used precisely. NEVER end a skill with a rote Checklist — a checklist survives only when it is about the artifact the skill produces. Upstream and vendored packs are copied as published and need not follow this style.

Agents and rules written here follow the same voice. An agent prompt opens with a role line and a `<system-conventions>` block stating the RFC 2119 contract with `NEVER`/`AVOID` as aliases for `MUST NOT`/`SHOULD NOT`, and repeats its `<critical>` rules at the start and the end. A rule opens with a bold one-line reason, then imperative bullets, and states what its trigger cannot see.

## Licensing

Third-party license texts and attributions live in [`licenses/`](./licenses/README.md), never inside a skill directory: a skill folder holds only what the skill loads at runtime. When a skill adapts third-party material, add its license or attribution under `licenses/` and a row to that folder's README. The root [`LICENSE`](./LICENSE) covers what is written here; vendored packs and `upstream/` copies stay under the terms their own files state.
