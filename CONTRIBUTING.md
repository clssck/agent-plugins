# Contributing

Maintainer documentation for this repository. The [README](./README.md) is a generated catalog.

## Maintenance

[`.github/workflows/sync-upstreams.yml`](./.github/workflows/sync-upstreams.yml) runs [`scripts/sync.ts`](./scripts/sync.ts) daily at 06:17 UTC and on relevant pushes. It pins and stages upstreams, regenerates the catalog, and commits only after the repository check proves that every declared skill, rule, agent, command, and tool is discoverable, generated rules and compatibility output are current, concrete `skill://` targets resolve, and skill names are unambiguous. This pass validates contracts; it does not execute a skill workflow.

The README is regenerated by the workflow on every run, so a local run leaves it alone. To update it locally: `GITHUB_TOKEN=$(gh auth token) bun scripts/sync.ts --readme`. `bun scripts/sync.ts --local` renders rules and runs the load check without network access or a token.

[`.github/actions/omp-loader-check`](./.github/actions/omp-loader-check/action.yml) checks out the commit pinned in [`omp-source-lock.json`](./omp-source-lock.json) and runs OMP's actual extension providers for skills, commands, rules, and tools, its fatal task-agent parser, and its extension module loader. [`.github/workflows/validate.yml`](./.github/workflows/validate.yml) runs it on pushes and pull requests; the sync workflow runs it with `bun test scripts` before committing, because pushes made with `github.token` do not trigger Validate. The lock watches the OMP docs and source files that define those contracts; scheduled drift detection opens an issue when they change.

Local development uses the shared default plugin store: run `bun install --cwd ~/Projects/agent-plugins`, then `omp plugin link ~/Projects/agent-plugins/packs/clssck-core` (and `packs/omp-development` when working on the OMP snapshot) to make working-tree edits live in normal sessions. OMP profiles do not isolate plugin links. Re-link the installed-copy path shown in the README to return to release behavior.

## CoCo compatibility (`coco@2`)

Packs in CoCo format are adapted by [`scripts/compatibility.ts`](./scripts/compatibility.ts), versioned by `COMPATIBILITY_VERSION` (currently 2). Generated upstreams opt in with `"compatibility": "coco"` in `sources.json`; committed `packs/coco-*` opt in with `ompCompatibility.profile` in their `package.json`. The layer is deterministic and runs only on copies in this repository; source repositories are never modified, so packaged text may differ from the original beyond link syntax.

- CoCo question aliases (`AskUserQuestion`, `ask_user_question`, `ask_question`, `multiSelect`) become OMP `ask` calls with `questions[]`, an intent, stable unique ids, object options, and OMP-native recommendation/`Other` semantics. Approval gates require an explicit user response.
- Known delegation shapes become OMP `task` batches; legacy task fields, implicit question payloads, unsupported `skill()` calls, and non-OMP todo names fail compatibility lint instead of shipping silently.
- `skill()`, `$skill-name`, and web-fetch aliases become OMP `skill://`/`read` instructions. External capabilities such as the `cortex agent-studio` CLI, `nipyapi`, `snowflake.connector`, and Snowflake-only tools receive an availability/authentication gate and must stop as blocked when absent; the adapter never invents a shell fallback.
- Missing Markdown references are repaired or de-linked. Concrete `skill://` roots and subpaths must resolve within the same pack or through a declared `ompSkillReferences.requires` provider; only targets declared in that pack's `ompSkillReferences.optional` list may be absent.
- `cortex-code-guide` is a product reference for Cortex Code itself, so its descriptions of Cortex Code tool names are preserved and excluded from OMP-instruction aliasing.
- `bun scripts/sync.ts --check` is read-only. Generated `package.json` records `ompCompatibility` (`profile`, `version`) and pinned `sync` provenance; checks reject stale output or mismatched metadata. `--local` regenerates rules and checks packages but does not rewrite committed CoCo packs. After editing the adapter, run `bun scripts/compatibility.ts --write packs/<pack>` for each affected committed pack; normal network sync rebuilds opted-in generated upstreams.

## Add an upstream

Append to `upstreams` in `sources.json`: `name` (the pack name), `repo` (`owner/name`), `ref` (branch), `sha` (any commit; the sync moves it), `description`, and `include`, which maps upstream paths to pack paths (usually `{ "skills": "skills" }`). Push, and the workflow does the rest.

## Add a pack of your own

Create `packs/<name>/package.json` with `name` (matching the directory), `version`, and `"omp": {}` (list TypeScript extension modules under `omp.extensions`). Add `skills/<skill>/SKILL.md`, `agents/*.md`, or `commands/*.md` as needed; OMP does not look inside subdirectories of `rules/`, `agents/`, or `commands/`.

## OMP development snapshot

`packs/omp-development/` is a reviewed snapshot of `can1357/oh-my-pi/.omp/{commands,skills,tools}`, not an automatic mirror. `omp-source-lock.json` records upstream Git object hashes. The scheduled `omp-source-drift` job compares those objects through GitHub's API and opens or updates an issue assigned to `clssck` when they change; GitHub sends email when issue-assignment email notifications are enabled.

Closing a drift issue dismisses that exact recorded upstream state; CI leaves it closed until one of the watched objects changes again. Leaving it open also produces no repeat notifications for the same hashes.

On a drift issue: review the linked upstream comparison, copy only intended changes, preserve the adaptations in `packs/omp-development/ATTRIBUTION`, move required tool dependencies to the root `package.json`, bump the pack version, then update `snapshotCommit` and every recorded object hash. Run `GITHUB_TOKEN=$(gh auth token) bun scripts/check-omp-source.ts`, `bun scripts/sync.ts --check`, and the pinned loader check before closing the issue.

## Rules

`packs/<pack>/rules/` is generated: edit `rule-sources/<pack>/*.md`, then run `bun scripts/sync.ts --local` and commit both. Shared regex fragments live in `rule-sources/fragments/<name>.regex` and are referenced in a rule's frontmatter as `{{<name>}}`; `shell-command-start` and `json-command-start` match the start of a shell command in raw and JSON-encoded tool arguments. A rule in `packs/<pack>/rules/` without a source fails the check. Rule fields live in `omp://ttsr-injection-lifecycle.md`; discovery and matching semantics in `omp://rulebook-matching-pipeline.md`. The rules OMP ships (`packages/coding-agent/src/discovery/builtin-rules/*.md` in the OMP repository) are the shape to copy: `description`, `condition`, `scope`, `interruptMode` frontmatter, then a one-line statement of the rule followed by a `## Avoid` / `// Bad` example and a `## Use` section with the corrected form, plus `## Exceptions` / `## Keep … when` where they exist. The rule name is the filename.

## Authored style

Skills written here follow OMP's project-skill semantics. Canonical prompt-authoring snapshots live in `packs/omp-development/skills/`; `omp://skills.md` defines discovery, layout, and runtime frontmatter. Use `name` plus a trigger-rich `description`. A skill that must remain slash-triggerable but hidden from automatic model invocation uses `disable-model-invocation: true`; do not add alternate discovery symlinks. Optimize descriptions for retrieval coverage, not a fixed word count. Use task headings for procedures, noun headings for reference material, tables for real enumerations, and executable examples where behavior depends on exact syntax.

Agents and rules use the same dense, imperative voice, not an identical heading template. Agent prompts take role, RFC 2119, and critical-edge guidance from `system-prompts`; bundled prompts under `packages/coding-agent/src/prompts/agents/` and `omp://task-agent-discovery.md` define their actual fields and discovery contract.

## Licensing

Third-party license texts and attributions live in [`licenses/`](./licenses/README.md), never inside a skill directory: a skill folder holds only what the skill loads at runtime. When a skill adapts third-party material, add its license or attribution under `licenses/` and a row to that folder's README. The root [`LICENSE`](./LICENSE) covers what is written here; vendored packs and `upstream/` copies stay under the terms their own files state.
